# 詳細調査プロファイル（develop 0.10.1-dev）

再生中の異常を、Windows内部、ドライバーとUSB転送、機器内の再生タイミング、物理出力のどこで生じるか調べるための取得です。回復操作・設定変更は自動実行しません。収集処理が完了したことと、必要な証拠が揃ったこと、原因が確定したことを区別します。

## 対象PCで一度に取る

1. アプリを閉じ、mainフォルダーで `start-develop.cmd` を実行します。画面の **0.10.1-dev** を確認し、記録を新規作成・再開します。
2. **2 条件を設定 → ノイズ発生中：USB＋Audioの設定へ** を押します。テスト音・内部録音・30秒・詳細ETL同梱を初期選択します。設定だけの操作で、まだ音や取得は始まりません。ETL同梱は書き出し画面で解除できます。
3. **音の調べ方**で実際に問題が出るWindows出力を選び、録音の同意を確認します。**次の切り分け**で追加診断の取得範囲と負荷を確認し、USB＋Audioの同意をチェックします。
4. スマホのカメラを先に回し、**3 調査する**の共通の開始を1回押します。管理者確認を許可し、「USBを開始」「Audioを開始」と進む表示を確認します。画面の時計は準備と録音を区別します。テスト音が始まり**同時記録中**と表示された区間をスマホでも記録し、ノイズ時刻を共通ボタンで残します。
5. 30秒後、または共通の終了で録音とトレースを止めます。**ETL停止後の追加情報・イベント読み取り検査**が終わるまで待ちます。選んだ出力の形式と再生状態は開始前に記録します。機器の親チェーン、ドライバー、電源、プロバイダー定義の詳しい調査は保存後に行い、実際に取得した時刻を残します。
6. **4 聞き直し・結果 → USB・Audio取得結果**で、ファイル保存とUSBイベント検査を別々に確認します。スマホの録画を同じ試験のPC録音へ関連付け、**詳細ETLも含める**を確認してZIPを書き出します。失敗時もZIPを持ち帰れます。

既に得られた正常実音は対照に使えます。HDMIへの往復や、確認済みの回復操作を繰り返すことは必須にしません。スマホからのLAN送信に手間取る場合は、カメラの元ファイルをUSB等でPCへコピーして取り込めます。

## 原因候補と証拠

| 仮説 | 自動で取る証拠 | 解析時の見分け方・限界 |
| --- | --- | --- |
| Windows再生・形式・音声拡張 | 選択出力の共有形式、既定/最小処理周期、音量・ミュート、再生セッション、FxProperties、Audio ETL | FxPropertiesは設定値で、稼働中APOの完全な証明ではない。基準音との自動比較と併せて使う。 |
| ドライバー・機器状態の変化 | 保存後のPnP親チェーン、サービス、デバイス/クラスのフィルター、PowerData、問題コード、関連ドライバーファイル版・ハッシュ、関連Systemイベント | ハッシュや版情報だけで信頼性・正常動作を断定しない。PowerDataはWindowsのCM_POWER_DATAバイナリ（Base64）で、USB電圧の実測ではない。 |
| USB転送・同期・バッファー | USBXHCI/UCX/USBHUB3のヘッダー・エラー・状態、初期状態イベントと対象機器対応、再生クロック/パケット時刻/バッファー残量 | USBペイロードは指定しない。ドライバー報告値と実際のDACクロックは別で、実音との照合が必要。 |
| 省電力・起動/復帰との関係 | 電源プラン全項目、power requests、機器電源プロパティ、起動情報、関連イベント | 保存後のスナップショット。収録中の全遷移を網羅するものではないのでETWと併用する。 |
| CPU負荷・DPC/ISR・スケジューリング | Audio＋GeneralProfile ETL、使用したWPRプロファイル定義、概ね5秒ごとのCPU/DPC/割り込みと音声状態 | 粗いサンプル値で瞬間的な遅延を除外しない。各取得の時間・負荷も保存し、取得処理自身の影響を残す。 |
| DAC/アナログ出力・録音側 | 基準WAV、内部録音、サンプル比較、関連付けたスマホ元音声/動画 | 内部録音が一致してもUSB・DAC・アナログ回路を単独で確定しない。正常実音との比較と位置合わせが必要。 |

`investigation-hypotheses.json`は、仮説ごとの必要証拠と、その取得時点の可用性を保存します。仮説が支持・棄却されたという自動判定ではありません。スマホの取り込みが後の場合は、最終session.jsonのphysicalRecordingsも照合してください。

## 保存されるファイル

すべて同じ `traces/<traceId>/` に置き、試験ID・録音ID・選択出力refに結び付けます。

- `trace.json`：開始/停止結果、録音開始の応答と時刻、対象機器、コマンドと実引数、終了コードの10進/16進、Windowsのエラー文、QPC/UTC、追加取得の進行と欠落項目、各ファイルのハッシュ。
- `trace.etl`・`usb.etl`：Audio＋GeneralProfileとUSBの生トレース。ZIP同梱は詳細ETLの選択に従う。
- `usb-providers.txt`・`usb-provider-schema.json`：実際のLogman入力と、対象OSの公開プロバイダー/キーワード/イベントテンプレート。各プロバイダーのテンプレートは最大1,000件、上限到達も記録する。
- `investigation-before.json`・`investigation-after.json`：機器・ドライバー・サービス・音声・電源・実行環境・WPR定義。
- `investigation-samples.json`：概ね5秒間隔、最大30回のCPUと音声状態。CPU項目は最大129行。実際の開始・終了時刻、所要時間、エラーを記録する。
- `investigation-events.json`：該当区間のSystemイベント最大2,000件から、USB/Audio/PnP/電源/WHEA等を最大300件。通常の情報イベントも対象。走査/保存の上限到達を明示する。
- `usb-validation.json`：先頭最大10,000イベントを読んだ結果、プロバイダーとイベント種別の件数、時刻範囲、初期状態による対象対応、読取失敗。全ETLの解析やイベント欠落数の測定ではない。
- `investigation-hypotheses.json`：必要証拠の一覧、取得可否、内部録音の比較等。スマホ時計の自動同期は行わない。

追加診断JSON・プロバイダー設定は通常ZIPにも入ります。Windowsのコマンド出力にはプロセス名等が入り得ます。ユーザーフォルダー名とUSBインスタンス末尾は伏せ、出力に上限を設けます。ネイティブコマンドは最大256件、通常の標準出力/エラーは各16,384文字、電源・プロファイル照会は各65,536文字で、打ち切りを記録します。Windowsコマンド出力はOSのOEMコードページで読み、使用した文字コードも保存します。原本・録音・ETL・解析は公開Gitへ追加しません。

## 再生クロックと内部録音

USB付きテスト音では、再生側の `IAudioClock` とバッファー残量・投入フレーム数を概ね100ms間隔、録音パケットの位置と時刻も概ね100ms間隔（不連続等のフラグ時は追加）で保存します。各最大4,096件で、取得の有効状態と上限到達も記録します。値はsession.jsonの `audioProbes[].capture.streamTiming` にあります。APIが提供しない場合はエラーを残します。

`DevicePosition`は`renderClockFrequency`と組み合わせて秒へ換算します。`ClockQpc100ns`と`PacketQpc100ns`は**100ns単位へ換算済みのQPC**、Query/ObservedQpcはcapture.qpcFrequency単位の生QPCです。同じ数値単位と仮定しません。`reportedRenderRateRatio`は、有効なS_OKサンプルの位置増加/報告周波数とQPC経過の比です。これはドライバーが報告した進みの要約で、物理DAC周波数の直接測定ではありません。S_FALSE・エラー・位置の逆行も保存し、バッファー残量0だけを可聴ノイズと判定しません。[Microsoftのクロック仕様](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclock-getposition)、[録音パケット時刻の仕様](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer)

内部録音と基準音は、同じサンプルレート・チャンネル数の場合、最初の非ゼロ部分で位置を合わせ、その後の全サンプルを比較します。`referenceComparison`に位置差、比較長、差分数、最大差を保存します。短すぎる場合、形式違い、無音、位置合わせが成立しない場合を分けます。音量・他アプリ・音声拡張・位置ずれも差分の原因になるため、差分をそのままノイズと呼びません。一致しても物理出力の正常は証明しません。

## 0.9.1-devの開始失敗からの修正

直接ETWセッションの作成に併用できない`--v`を除去しました。同じコマンドで発生した0x80070057の引数エラーを開発PCで再現し、除去後は非管理者の権限チェックまで進むことを確認しています。また、ランダムな未登録テストプロバイダーを使う実Logmanの開始・停止で、正確なファイル名のETLとハッシュが得られることを確認しました。この試験は実USB通信を記録しません。生のUSBイベント取得の成否は、対象PCの結果で改めて確認します。開始失敗後の後片付けも、その試行の固有セッション名だけへ行い、開始と後片付けの終了コードを分けて残します。

テスト音が開始しなかった試行は「判定できず」として、マーカー0件や古い版のNoReproを正常・改善の根拠にしません。設定変更や回復操作を追加で行う前に、まず同じ症状中の取得を成立させます。


## USB・Audio開始とテスト音の連携

USBとAudioの開始後、取得プロセスは画面から録音開始の応答を最大30秒待ちます。設定した収録時間は応答後に数えます。終了を先に押した場合や応答期限を過ぎた場合は、先に開始したトレースを保存し、内部録音の結果を別に示します。応答期限は管理者確認やWindowsの開始・保存処理全体の上限ではありません。

公開済みの開始前スナップショットは互換性のため読めます。新しい調査では準備の短縮を優先し、詳細な設定・状態は保存後の値と明示します。転送の関連付けはETL内のイベントと照合します。保存までにデバイスを挿し直した場合、対応が未確定のまま残ることがあります。
