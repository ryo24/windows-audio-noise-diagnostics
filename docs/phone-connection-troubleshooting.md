# スマートフォンがQRのページを開けないとき

PCが有線LAN、スマートフォンがWi-Fiでも、ルーター内で端末間通信が許可されていれば利用できます。同じルーターにつながっていても、ゲストWi-Fi、端末分離、VPN、PCのファイアウォール等によって通信できない場合があります。接続失敗と録音の制限は別の問題です。まずページが開けるかを確認します。

## 音を先に記録する方法（LAN接続不要）

ノイズが再現している間に、スマートフォンのカメラでスピーカー近くの動画を10〜30秒撮ります。PCのテスト音声・内部録音も同時に動かし、ノイズが聞こえたらPCの共通ボタンを押してください。録音位置・音量を途中で変えず、音割れしない距離にします。

USBケーブル等で元の動画をPCへコピーし、**3 調査する → スマホをつなぐ → ファイルを取り込む**で取り込みます。確認は**4 聞き直し・結果 → スマホなどの実音**です。ノイズが出ないと確認できたHDMIや別の機器で聞き直してください。スマートフォン側の元ファイルも保持します。クラウドやブラウザーの権限変更は不要です。

内部録音にノイズがなくても、ドライバー・転送・アナログ回路のどこかを単独で確定したことにはなりません。スマートフォン側の録音処理、周囲音、PCとの時計の違いも考慮します。

## 先に試す比較

1. PCで受付を開き直し、**最新のQR**を使います。受付は15分で終了し、再開ごとにポートとURLが変わります。古いタブのURLは使いません。
2. PCで選んだIPが、使用中のEthernet／Wi-Fiのものか確認します。候補にはアダプター名・種別・ゲートウェイ有無を表示します。VPNや仮想アダプターを誤選択していないか見ます。
3. 同じ受付・同じURLを、スマートフォンのFirefox BetaとChromeで比較します。「どちらも開かない」「Chromeだけ開く」を記録します。前者でもルーター原因とは断定しません。
4. URLの先頭が **`http://`** のままか確認します。この受付はHTTPSには対応していません。HTTPS-Onlyの警告が出る場合、信頼するLANのこの受付に限って「HTTPサイトへ進む」に相当する操作を使います。ブラウザー全体の保護を無効にする必要はありません。[MozillaのHTTPS-Only説明](https://support.mozilla.org/en-US/kb/https-only-mode-firefox-android)
5. Firefoxの **メニュー → 設定 → サイトの設定 → ローカルネットワークのデバイス** に対象の拒否が残っていれば、そのサイトの許可を確認します。表示名や項目の有無はバージョンで異なり、項目がないだけで異常とは判断しません。Android側のFirefox Betaの権限画面にローカルネットワークに相当する項目がある場合も確認します。[Mozillaの権限説明](https://support.mozilla.org/en-US/kb/control-personal-device-local-network-permissions-firefox-android)
6. スマートフォンのWi-Fiがゲスト用でないか、VPN・フィルターの有無、Windowsが使用中のネットワークをどう分類しているかを確認します。ファイアウォール全体を無効にせず、必要なら信頼するプライベートLAN上の受信アプリだけを許可します。ツールはルール・ネットワーク分類を自動変更しません。

通常のLAN HTTPではページ内のマイクAPIに制限があります。ページが開けたら、端末のカメラ・録音アプリへの引き渡し、または保存済みファイル選択を使います。詳細は[実音取り込みの手順](physical-capture.md)を参照してください。

## アプリで診断を保存して渡す

受付を動かしたままスマートフォンで失敗を再現し、PCで **接続診断を保存** を押します。自己テストの結果が出たら、スマートフォン／ブラウザー、別ブラウザーとの比較、画面のエラー文を入力して **診断を記録へ保存** を押します。その後受付を止め、**5 書き出す**からZIPを作ります。別PCへの受け渡しは[データ管理](data-workflow.md)のinboxを使います。

| 保存される観測 | 判断できる範囲 |
| --- | --- |
| PC内HTTP自己テストの応答 | PC内で受付に応答できたか。スマホからの到達やファイアウォール通過の証拠ではない |
| PC以外からのTCP接続 | 別端末の通信が届いたか。スマホの特定やページ表示の成功までは示さない |
| HTTP要求・応答と理由 | ページ／スクリプト／アップロード等の分類、HTTPの応答コード。PC内アクセスも含むのでPeerも見る |
| HTTPポートへのTLSらしい通信 | HTTPSへ変換された可能性。Firefoxや原因をこれだけで特定しない |
| 取得できなかった情報 | unavailable／エラー種別として保持。空の正常結果にしない |

**別端末の接続が0件でも、Firefoxが原因とは断定しません。** ブラウザーの許可、端末の接続先、IP、VPN、Windows、ルーターのいずれでもPCへ届かなくなります。別端末のHTTP応答があっても、画像やスクリプトの失敗、スマホ側の表示失敗は別途確認します。

接続履歴は1受付につき直近200イベント、接続数は受付単位です。保存前はメモリー内だけにあり、受付を再開すると新しい履歴になります。停止後もアプリを開いている間は直前の受付の診断を保存できます。**失敗を再現した後、受付を再開・アプリを終了する前に保存**してください。最後の要求エラーは、成功後も履歴として残ることがあります。

保存操作を選んだ場合だけ、選択したPCのLAN内IPv4・ポート、アダプター種別、ゲートウェイ有無、取得可能なネットワーク分類・ファイアウォールのプロファイル状態、接続分類、ブラウザー系統とメジャー版、手動メモを記録します。受信元IP、MAC、SSID、PC名、受付URL／トークン、Cookie、全User-Agentは保存しません。メモ内の受付URLは省略処理しますが、自由入力全般の個人情報を完全に除去する機能ではありません。保存した診断は`session.json.networkDiagnostics`に追記し、`network-diagnostics.json`と報告書にも出力してZIPへ含めます。公開Gitへ追加しないでください。

## Firefox Betaのエラー詳細を見る（Android・USB）

「正常に接続できませんでした」はHTTPステータスとは限りません。HTTP応答前の失敗には404や500のようなコードが存在しないため、**エラー名・表示文、HTTP応答の有無**を記録すれば構いません。コードを無理に探す必要はありません。

詳細が必要な場合は、PC側Firefoxの開発ツールからAndroidのタブを調べます。

1. PixelのAndroid設定で開発者向けオプションを有効にし、USBデバッグを有効にします。
2. PixelのFirefox Beta設定で「USB経由のリモートデバッグ」を有効にし、データ通信可能なUSBケーブルでPCへ接続します。Pixel上にPCを許可する確認が出たら、自分のPCであることを確認して許可します。
3. PCのFirefoxで `about:debugging` を開き、「USBデバイスを有効化」を選びます。端末が出ない場合はデバイスを更新します。PC・端末のFirefoxの版は対応するものを使います。表示されない場合はMozillaの手順に従いADBやUSBドライバーを確認します。
4. PixelでQRのURLを開き、PC側でPixelのそのタブの **調査／Inspect** を選びます。ネットワーク（Network）を開いてページを再読み込みします。
5. 失敗した要求の状態欄、表示されるエラー名、コンソールの関連エラーを控えます。HTTPコードが空でも、接続拒否・タイムアウト等の文言があればそのまま伝えてください。エラーページで要求を捕捉できない場合は「捕捉できなかった」と記録し、PC側の接続診断を使います。
6. 調査後はUSBデバッグ／Firefoxのリモートデバッグを元に戻します。

送るものは、Android版・Firefox Beta版、Chromeとの比較、エラー文または画面写真、アプリが出力した診断ZIPで十分です。画面写真のURL内の`/s/`より後のトークンは隠してください。HARや生のネットワークログには受付URLやCookie等が含まれ得るため、そのまま公開Issueへ投稿しないでください。

手順の一次資料：[MozillaのUSBリモートデバッグ](https://firefox-source-docs.mozilla.org/devtools-user/about_colon_debugging/)、[Network Monitor](https://firefox-source-docs.mozilla.org/devtools-user/network_monitor/)。確認日：2026-11-23。実機のPixel 9／Firefox Betaでの接続可否は開発環境では未検証です。
