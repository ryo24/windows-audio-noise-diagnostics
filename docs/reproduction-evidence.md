# 再現時の経路・ドライバー・時間軸を調べる

HDMIへ変更すると止まり、3.5mmへ戻すと再発することが確認済みなら、その旨を「確認済みの症状」へ書きます。今回の調査で同じ往復比較を必須にする必要はありません。未取得の内部録音と実音、再現時の構成、時刻を優先します。

## 再現時の構成と再生条件

テスト開始前に「2 条件を設定 → 再生条件のメモ」へ素材・再生箇所、アプリの出力設定、PC／アプリ／機器の音量、音声拡張、直前の操作・スリープ復帰・負荷を記入します。再生アプリ名は比較テストの欄にも記入します。未確認は未確認のまま保存でき、ツールは設定を変更しません。

各テストでは以下を保存します。

- 開始側・最初のノイズマーカー・観察終了側のアクティブな音声出力と共有再生セッション。プロセスIDと実行ファイルの名前だけを取得し、ウィンドウタイトル・コマンドライン・実行ファイルのフルパスは通常ログへ保存しません。
- テスト開始後のバックグラウンド取得：音声デバイスと親デバイス、ドライバーの版・日付・INF、起動情報、直近の復帰イベント、粗いCPU負荷。取得区間は記録され、開始と完全に同時の構成とは扱いません。開始直後にアプリがまだ再生していなくても、最初のノイズマーカーで別途セッションを取り直します。
- テスト音声・録音で選んだ出力は`audioProbes[].playbackSnapshot`に保存し、既定出力や他アプリの出力と区別します。

`playbackSnapshots[].data.outputs[].endpointRef`を、同じセッション内の`context.audioDevices.data.devices[].ref`へ結合し、`parentRef`を辿ると物理デバイスとドライバーを照合できます。関連が未公開・未取得の場合は空欄やunavailableを残します。表示名が似ているだけでUSB音声ドライバーと断定しません。Activeなセッションは無音でも存在し、独占モード等は見えない場合があります。アプリの手動出力設定も併記してください。

## 同じ再現区間を録音する

「2 条件を設定」でテスト音声・Windows内部の音・対象の3.5mm出力を選び、「3 調査する」で開始します。同時に[スマートフォン](physical-capture.md)等でスピーカー音を記録します。マイク入力を選ぶこともできますが、この版ではPC内のループバックとPCマイクを同時に二重録音するUIにはしていません。内部録音と実音を同時に比べるにはPCループバック＋スマートフォンを使います。

聞こえたノイズはその場でボタンを押します。操作イベントのUTCとQPC、録音開始・終了のQPCと周波数を保存するため、同じPC起動中ならノイズボタンと録音の相対位置を計算できます。手動ボタンには人の反応遅れがあり、サンプル単位のノイズ発生時刻ではありません。WAVの補完無音、不連続フラグ、録音開始遷移も考慮してください。

スマートフォンの録音時刻はPCと自動同期しません。音声に含まれる共通の開始音や同じ素材を手がかりに人または解析ツールで照合します。受信時刻は録音開始時刻ではありません。録音後はHDMIや別PCなど正常と確認できる経路で聞き直し、実際の音と同じか記録します。内部録音がきれいでもループバック位置によって未収録のデバイス処理・転送・アナログ回路が残るため、アナログ回路と断定しません。

## 時間の扱い

v0.6以降の通常テストの`durationSeconds`は単調時計QPCによる観察時間です。テスト終了ボタンで確定し、結果入力中や終了後のBluetooth保存によって延びません。`timing.wallSeconds`と`clockDifferenceSeconds`にUTC差と経過時間の差を記録します。v0.7以降は終了後に結果入力を閉じた場合、中断として保存し、録音・観察を再開しません。

`timeline.csv`と`session.json.timeline`にはテスト開始・観察終了・中断、ノイズボタン、録音要求、実音ファイル受領を記録します。録音の実開始・終了は`audioProbes[].capture`のUTC/QPCを使います。録音要求と実開始は別です。QPCの周波数は保存値を使い、再起動・別PC・スマートフォンをまたいだ差を計算しません。古いログは原本を変更せず従来の値を残します。

## 音声グリッチ・DPC/ISRの詳細トレース

通常の記録と録音で絞れない場合に使います。「3 調査する → 詳細トレース（任意）」で説明のチェックを入れ、**WPRを60秒間追加取得**を押すと管理者権限の確認後、WindowsのWPRを使います。WPRの`GeneralProfile`と`Audio`をメモリーモードで取得し、60秒または停止要求でETLへ保存します。ツール更新やドライバー変更・再起動は行いません。

他のWPRと区別するランダムな`-instancename`を全コマンドに付け、既存のトレースを`-cancel`することはありません。競合や権限不足、プロファイル未提供なら失敗を残します。メモリーモードは古いイベントが失われる場合があるため、再現直前に開始して短く記録します。取得負荷も再現条件へ影響するので、取得なしの観察と区別します。

v0.8以降は管理者ヘルパーを開く前に実行ID・保存先を確保するため、開始直後に「WPRを停止して保存」を押しても要求を失いません。開始前に受け付ければETLなしの中止とします。画面は「要求の受付待ち」「ETL保存中」「停止・保存完了」「失敗」を継続更新します。完了は状態ファイルと実在する正のサイズのETLの一致で判定し、昇格したプロセスの終了検出だけに依存しません。

停止受付を15秒確認できない場合、または保存開始から120秒以上応答がない場合は、経過時間と未確認であることを表示します。長い保存を勝手に強制終了したり、成功として扱ったりしません。「WPRの保存先を開く」で`trace.json`の`status`、`updated`、`instanceName`、`startExitCode`、`stopExitCode`とETLを確認できます。ヘルパーが完了状態を残さず終了した場合は`HelperExited`と終了コードを残します。保存途中のETLは完成したトレースとして解析しないでください。

ノイズボタンの元のUTC・QPC・イベントIDを、後からETWマーカーへ送ります。`trace.json`にはマーカー送信側の時刻と終了コードも残すので、ETWマーカーの発行時刻をクリック時刻と同一視しません。通常ログが失敗していたりWPRのイベントが欠落したりする可能性も含め、WPAでAudioグリッチとDPC/ISRの時系列を確認してください。

`traces/<id>/trace.json`と`trace.etl`が成果物です。ETLにはプロセス名・ファイルパスなど通常ログより広い情報が含まれる可能性があり、ZIPには既定で含めません。必要な場合だけ「詳細ETLも含める」を選びます。ETLの中身は自動解析・原因断定しません。WPAのインストールも自動では行いません。

停止に失敗した場合は`trace.json`の`instanceName`と`stopExitCode`を確認します。管理者のPowerShellから `wpr -status -instancename <instanceName>`、必要なら `wpr -stop <保存先.etl> -instancename <instanceName>` で**そのインスタンスだけ**を確認・保存してください。全体への`wpr -cancel`を使わないでください。PC再起動やヘルパー強制終了時にはETLが未保存になり得ます。

USBの転送失敗・パケットまでを全機種で取得するプロファイルではありません。USB専用ETWが必要なら、デバイスがUSB接続である証拠と上記ETLを先に確認し、MicrosoftのUSB向け手順で対象プロバイダーを選びます。独自の未検証プロバイダーをツールが自動で一括有効化することはありません。

v0.9以降は「次の切り分け」のUSB＋Audioで、xHCI系USBプロバイダーの転送ヘッダーを追加取得できます。通常のWPRとは別の同意・明示的な選択が必要で、共通の調査操作に連動します。旧スタックや全機種の取得を保証するものではありません。[USB追加調査](usb-follow-up.md)の範囲・保存・復旧方法を確認してください。
