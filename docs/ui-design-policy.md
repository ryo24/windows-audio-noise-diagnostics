# UI設計の方針

この文書は、UIを変更するときに参照する設計上の判断基準です。操作方法は[画面の使い方](user-guide.md)、録音・データ管理の仕様は各機能の文書を参照してください。

基準となる実装はv0.7.0（`ca50ff7`）です。画面数や配置を永久に固定するための文書ではありません。今後の変更でも、利用者が次の操作とその結果を判断できることを守ります。

## 解消したい問題と設計の目的

以前は、画面下部の「テスト開始」と音声タブの「再生・録音を開始」が別に存在していました。利用者は、どちらを先に押すか、両方必要か、片方を止めると何が終了するかを、内部の仕様や過去の説明から判断する必要がありました。

今後は、**利用者が内部の機能構成を知らなくても、一つの目的に対して次に押すボタンを判断できるUI**にします。説明文を増やすだけで解決せず、操作の統合・配置・状態遷移で迷いを減らします。

## 利用者に見せる単位

| 単位 | 意味 | UI上の扱い |
| --- | --- | --- |
| セッション | 一連の比較・録音・取得情報を保管する記録 | 準備画面で新規作成・再開する |
| 一回の調査 | 一つの条件で観察し、ノイズ時刻と状態を記録する区間 | 共通の開始と終了で扱う。録音を含めるかは事前に選ぶ |
| 聞き直し | 保存した音を再生して、実音と照合する作業 | 調査の実行と分ける。新しい観察や録音を始めない |
| 追加取得 | スマホからの受信、WPR等の補助機能 | 必要な場合だけ使う。通常の調査開始との違いを明示する |

バックエンドで比較記録・音声・Bluetooth収集が別々の処理になっていても、その境界をそのまま別の開始ボタンとして利用者へ見せません。ログではそれぞれの実際の開始時刻やIDを保持し、操作を統合したことを完全な同時刻取得と混同しません。

## 守る原則

### 1. 利用者の目的を選んでから、一つの操作で実行する

「テスト音声で調べる」「普段のアプリの音を録る」「録音なしで観察する」を実行前に選べるようにします。開始は同じ場所の一つのボタンで、必要な録音・観察・状態記録をまとめて開始します。

同じ調査に対し、「比較を開始してから、別のタブで録音も開始する」といった二段階の開始判断を復活させません。ノイズを記録するボタンも共通にし、対象の比較と録音へ関連づけます。

### 2. 主操作は、その目的の画面に置く

設定は設定画面、実行は調査画面、再生確認は聞き直し画面、ZIP出力は書き出し画面へ置きます。関係のない画面でも常に開始・ノイズ・終了ボタンを見せる構成を避けます。

移動と実行を区別します。「調査画面へ」は画面移動であり、録音や観察を始めません。「聞き直しを停止」と「調査を終了」も、止める対象が分かる名前にします。

### 3. 終了の意味を揃える

録音ありの調査では、手動終了で録音と観察を一緒に止めます。録音の時間・サイズ上限や失敗で録音が終了した場合も、観察を終了する流れへ進めます。「録音だけ終わったが、比較は知らないうちに続いている」状態を通常操作にしません。

終了要求から保存完了までは別の状態として表示します。その間の二重終了や追加マーカーを防ぎ、結果入力や関連情報取得を待った時間を観察時間へ加えません。結果入力を閉じても録音を勝手に再開せず、未確定の結果として残します。

### 4. 状態と次の操作を画面で説明する

待機、調査中、終了処理中、情報取得中、聞き直し中を区別します。無効なボタンの色だけに説明を任せず、「何が不足しているか」「どの画面で何をするか」「完了を待つ必要があるか」を短く表示します。

スマホ受信やWPRが別の画面でも動いている場合は、その状態が分かる表示を残します。表示する条件・経過時間・ボタンの有効状態は、同じ実行状態に基づいて更新します。

別プロセスへ送った要求、相手が受け付けた状態、実際の保存完了を分けます。「要求しました」を完了表示にせず、応答待ちの経過時間と未確認であることを示します。WPRは開始前に実行IDと保存先を確保し、その実行だけへ停止要求を送ります。状態ファイルを継続して読み、ETLの存在とサイズを確認して完了とします。状態更新が止まった場合や子プロセスが終了した場合は、永続的な要求待ちにせず、未確認・失敗と保存先を見せます。保存に時間がかかることだけを理由にトレースを強制終了しません。

スマホの送信でも、ブラウザーが送出した量とPCが保存を確認した状態を分けます。ファイルの読み出し失敗、HTTP拒否、応答なしを区別し、応答なしだけでファイアウォールや権限が原因と断定しません。許可の名称と確認場所を接続前に示します。送信できないときのログは、その送信経路に依存せずダウンロードし、PCで明示的に取り込めるようにします。ログの選択と記録への保存も分けます。

### 5. 必須の流れと追加調査を分ける

通常の調査を進めるために、BIOS確認、WPR、スマホ接続等を必須にしません。追加機能は「任意」と分かる場所へ置きます。

追加機能の操作名には対象を含めます。例えば「スマホからの受信を開く」は送信先を開く操作、「WPRを60秒間追加取得」は補助トレースの操作です。これらを一般的な「開始」だけで表しません。

### 6. 選択と許可は、実行から分ける

録音範囲の確認チェックは許可の操作であり、録音開始ではありません。チェックや画面移動だけで音声を流したり、マイクを使い始めたりしません。

録音方式やデバイスを変えた場合は範囲を確認し直します。録音なしの方式では、不要な録音設定・許可チェックを無効にし、それらを開始条件にしません。

確認のチェック欄には、何が対象か、チェック前に何をすればよいか、どこをクリックするか、チェック後にどう進むかを近くに示します。「確認しました」という文言だけで、利用者に事前テストや別の設定操作を推測させません。

### 7. 聞き直しと調査時の再生を区別する

聞き直し専用の画面と出力選択を用意します。調査時の出力を変更しなければ別経路で聞き直せない構成にしません。保存音声の再生を、新しい調査の観察や録音へ混ぜません。

「実際に聞いた音」「録音を再生した音」「両者の一致」を分けて入力します。PC録音を最後まで再生した事実と、スマホ等の記録を人が確認した申告も区別します。録音がない場合は、空の再生画面へ誘導するのではなく比較結果を見せます。

録音・元のテスト音・取り込んだ実音をアプリから再生する前には、ノイズがないと確認済みの出力へ切り替える案内を出します。同じ出力ならその点も明記します。「出力を変更するため戻る」を既定にし、利用者が明示的に選べば現在の出力でも再生できます。別の出力を選んだだけでは正常と判定しません。警告から戻る操作で再生や過去の照合結果の消去を行いません。報告書をブラウザーで直接開く場合は、アプリの確認ダイアログを通らないことも説明します。

### 8. 診断の限界と証拠を保つ

手動申告、自動取得、未取得、取得失敗を区別します。短時間ノイズがなかったこと、内部録音がきれいだったこと、通常イベントが0件だったことを、UIが正常・解決と断定する根拠にしません。

条件変更や画面移動で過去の記録を黙って上書きせず、別の比較として追加します。利用者が確認済みと明示した事項を、UIの進行条件を満たすためだけに再試験させません。

## 現在の画面構成と遷移

| 段階 | 責務 | 次へ進む契機 |
| --- | --- | --- |
| 1 準備する | セッションの新規作成・再開、機器と確認済み症状の記録 | 新規情報取得後は設定へ。既存記録の結果・書き出しにも移動できる |
| 2 条件を設定 | 調べ方、録音元・出力、比較条件、Bluetooth、再生条件のメモ | 調査画面へ移動する。ここでは記録を開始しない |
| 3 調査する | 条件確認、共通の開始・ノイズ・終了、任意の追加取得 | 終了と保存処理の後に結果入力へ進む |
| 4 聞き直し・結果 | PC録音・スマホ等の実音の確認、比較結果の閲覧 | 次の条件設定へ戻るか、書き出しへ進む |
| 5 書き出す | 報告書、記録フォルダー、必要なデータのZIP化 | 生成したZIPをエクスプローラーで選択する |

番号は基本の順序を示すもので、過去の結果を見るために毎回全段階の実行を強制するものではありません。画面数やタブ構成を変える場合も、これらの責務と次の操作が利用者に伝わる構成を維持します。

| 実行状態 | 主な操作と制約 |
| --- | --- |
| 準備不足 | 不足と解消先を表示し、開始を無効にする |
| 開始可能 | 選んだ調べ方が分かる一つの開始ボタンを有効にする |
| 調査中 | 条件変更と再度の開始を防ぎ、共通のマーカーと終了要求を使えるようにする |
| 終了処理中 | 観察時間を確定し、二重終了・追加マーカーを防ぎ、保存待ちを表示する |
| 結果・確認 | 保存された記録を確認する。次の調査やZIP出力は必要な取得・保存の完了後に行う |

## UIを変更するときの進め方

1. この文書と[操作ガイド](user-guide.md)を読み、利用者が迷う場面・達成したい作業・現状の操作数を具体的に書きます。
2. 通常の流れと、録音なし・取得失敗・中断・過去記録の確認等の分岐を整理します。追加機能を主操作の別の開始判断にしないか確認します。
3. 画面上の操作と、内部の開始・停止・保存を対応づけて実装します。既存データとの互換性と、実行状態の整合を保ちます。
4. 該当する操作検証と表示確認を行い、結果を変更説明に残します。文言・手順が変わる場合は操作ガイドも同じ変更で更新します。
5. 方針自体を変更する必要がある場合は、解消する問題、代替案、変更する原則・遷移、検証結果を明記し、この文書も同時に更新します。画面数・ボタン位置だけを固定理由にせず、判断できる操作の流れを優先します。

## 変更時の確認項目

- 初めて見る人が、画面だけで次の操作と開始できない理由を判断できるか。
- 一回の調査に別々の開始操作を要求していないか。マーカーと終了の対象が明確か。
- 録音あり・録音なしの両方で進めるか。録音範囲の確認と実行を混同していないか。
- 自動終了、手動終了、取得中の終了要求、途中で閉じる操作で記録が食い違わないか。
- 聞き直しを新しい調査に混ぜず、別の出力でも確認できるか。
- 再生前に出力の影響を案内し、戻った場合に再生や照合結果の上書きをしないか。
- WPRの即時停止、保存中、保存失敗、状態通知の途絶、子プロセスの異常終了を区別できるか。
- スマホの接続診断でPC内の自己テストと別端末の到達を区別し、保存範囲を明示しているか。
- 任意機能を使わなくても通常の流れを完了できるか。動作中の追加取得が見えるか。
- 過去の結果を見たり書き出したりするために、新しい調査を強制していないか。
- スクロール・ウィンドウサイズ・文字の折り返しを確認し、説明や必要な操作が隠れていないか。
- 操作ガイド、ボタン名、実際の動作、検証内容が一致しているか。

確認は変更に関係する範囲で行います。ドキュメントだけの変更で、無関係な実機録音等を一律に実行する必要はありません。
