# 内部録音に現れない変化の追加調査

内部録音が基準音と一致しても、実音に変化があれば、録音取得点より後段と実音の録音処理を調べる必要があります。この画面は原因を確定するものではなく、USB転送、良好な実音対照、Windows形式の比較に必要な記録を揃えます。特定機種やメーカーに限定しません。

## 1. 問題が出る出力でUSB＋Audioを取る

1. 「1 準備する」で記録を作成・再開し、**2 条件を設定 → 次の切り分け → USB転送＋Audioを同時取得**を選びます。
2. 「共通テスト音声・30秒に設定」を押し、**音の調べ方**で実際に問題が出るWindows出力を選びます。手動の接続欄と、実際に選んだWindows出力は別の証拠です。録音範囲を確認して了承します。
3. 「次の切り分け」でスマホが拾う接続・位置を記入し、必要なら比較先の調査を一覧から選びます。USBの取得範囲と負荷を読んで了承します。これは録音の許可とは別です。
4. スマホの録音・カメラを用意し、**3 調査する**の共通の開始を1回押します。録音と観察に加えて、管理者ヘルパーでUSBとAudioの取得を始めます。Windowsが管理者権限を求めたら確認します。追加のWPR開始ボタンを押す必要はありません。
5. 同じ区間をスマホで撮影・録音します。ノイズが聞こえたら共通のボタンを押します。受付の接続に時間をかけたくなければ、端末に動画を保存してUSB等で後から取り込めます。
6. 共通の「終了して結果を記録」、または指定した録音時間で録音と観察を終了し、その調査に関連するトレースにも停止・保存を要求します。詳細トレースの状態が保存完了になるまで待ちます。追加USB調査は30秒または60秒で行います。

管理者確認等のため、録音とトレースの開始は完全な同時刻ではありません。USBが始まる前の音をUSB転送と照合したことにはしません。`followUp.traceCoverage`には、確定した録音区間とUSB区間の重なりをQPCで計算して残します。USB開始点はコマンド成功の確認点であり、ETLヘッダーの開始点そのものではありません。実イベントの照合にはETLの時刻を使います。

## 2. 良好な出力を同じスマホで記録する

「次の切り分け」で**良好な出力を同じスマホで記録**を選び、比較先の調査を一覧で指定します。HDMI等、または同じ出力が回復した状態で、同じ基準音を再生して同じスマホで実音を記録します。スマホのアプリ・録音方式・位置・音量等はできる範囲で揃え、その条件を記入します。同じ出力の正常録音が既にあれば対照として使えるので、HDMIへの変更や正常録音の撮り直しを必須にはしません。

目的は、実音の録音処理が同じ変化を作っていないかを比較することです。HDMIから3.5mmへ戻すと再発することが確認済みでも、この実音対照は別のデータです。既知の往復再現をUIの都合でやり直すことは求めません。USB取得の許可はこの対照の必須条件にしません。

「4 聞き直し・結果 → PCで録音した音」で対応する録音を選び、その状態でスマホのファイルを取り込むと、終了後でも録音IDとテストIDを保存します。取り込む前に選択した記録を確認してください。再生確認では正常と確認できた経路を使い、ファイル内の音と再生時に加わる音を区別します。

## 3. Windows形式を一つ変える比較（任意）

**Windows形式を1つ変えて比較**では「Windowsのサウンド設定」を開き、対象出力が提供する形式だけを手動で選びます。元の形式と変更後の形式を記入し、ほかの条件は揃えます。アプリはWindows設定、ドライバー、BIOSを変更しません。終わったら必要に応じて元の形式へ戻します。

各録音の`selectedOutputFormat`は、選んだ出力から読み出した共有モード形式です。既定出力の値や、基準WAVの48kHzとは区別します。物理DACのクロックを直接測った値ではなく、対応形式がない場合もあります。取得失敗はunavailableとして残します。

## 4. 再起動等で状態が変わったとき

**状態変化・回復条件を比較**では、直前の操作を「操作なし」「再起動のみ」「音声デバイスの無効・有効のみ」「スリープ・復帰のみ」「複数の操作」等から選び、開始時の発生状態も記入します。これらは利用者の申告で、操作時刻や実行を自動的に証明する値ではありません。起動後の経過等は従来どおり再現時のcontextへ別途取得します。

再起動とデバイスの無効・有効を続けて行って回復した場合は、「複数の操作」を選びます。次に再発した際、操作前の音を保存したうえで一度に一種類を変え、同じ出力で操作後の音を記録すると、回復条件を区別しやすくなります。今ある正常録音をやり直すことや、わざと再発させることは必須ではありません。アプリは機器の無効化や再起動を実行しません。

再起動前後で別セッションになった場合は、比較先の**別の記録から選ぶ**から元のsession.jsonを開き、終了済みの調査を選びます。元のJSONは変更せず、比較先のセッションID・テストIDと元JSONのハッシュを記録します。比較元の録音自体を現在のZIPへ自動コピーする機能ではないので、解析には元のZIPも保持してください。匿名endpointRefやQPCを別セッション間で直接同一視しません。

## 基準音と時刻の照合

追加調査では`audio-noise-reference-v2-indexed-...`を使用します。従来の定常音を維持し、各10秒区間の先頭1秒に、区間番号を示す6ビットの短い音を付けます。下位ビットから700／1400Hz、0.08秒から0.12秒間隔・各0.06秒で番号1からを示します。元WAVと`referencePattern`を保存するので、途中から録った実音でも区間を区別できます。短い符号音自体が解析用の基準音です。

参考音源の形式は48kHz・ステレオ・PCM16、最大振幅は従来と同じ約0.08です。生成秒数は観察時間を10秒単位で切り上げます。追加調査以外は従来のv1を維持します。v1とv2を同一のWAVとして扱わず、比較時は各referenceId・実際の出力形式・リサンプリングを確認します。スマホとPCの時計を同期したり、録音波形を自動照合したりする機能ではありません。

## 取得範囲・保存・解析

USB取得はWindowsのLogmanを使う独立したETWセッションです。USBXHCI／UCX／USBHUB3の公開キーワードからDefault、USBError、HeadersBusTrace、Rundownを解決し、256MBの循環ファイル、QPC時計で取得します。キーワードが未提供なら失敗を表示し、無制限の取得へ切り替えません。詳細は[MicrosoftのUSB取得手順](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/how-to-capture-a-usb-event-trace)と[Logmanのオプション](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/logman-create-trace)を参照してください。

対象はxHCI系スタックで、xHCIに接続されたUSB 2機器も含みます。選択した音声機器だけに絞るフィルターではありません。PartialDataBusTrace／FullDataBusTraceは指定しませんが、記述子や機器識別情報などがETLへ入り得ます。旧USBPORT／USBHUBスタックの専用取得は行いません。循環記録の上書きやプロバイダーの実装により必要なイベントが欠ける場合があります。取得の成功・イベント0件だけで正常や原因を断定しません。

成果物は`traces/<trace-id>/trace.etl`（従来のAudio＋GeneralProfile）、`usb.etl`、両者の状態・範囲・ハッシュを持つ`trace.json`です。テストの`followUp`、トレースの`link`、録音の`testId`、実音の`audioProbeId`／`testId`で関連を辿れます。USBの取得・保存失敗をAudio側の成功で置き換えません。

**5 書き出す → 詳細ETLも含める → ZIPを書き出して場所を開く**で、USBとAudioのETLを含めて持ち帰ります。既定では両方のETLを除外し、除外したパスをbundle.jsonに記録します。録音・動画・ETLは公開Gitへ追加しないでください。

ヘルパーが異常終了した場合、ETWセッションが残ることがあります。`trace.json`の`instanceName`と`usb.instanceName`を確認し、管理者のPowerShellで**そのインスタンスだけ**を調べます。USBは`logman query <usb.instanceName> -ets`、停止は`logman stop <usb.instanceName> -ets`です。WPRは[既存の復旧手順](reproduction-evidence.md)を使い、全体へのcancelは行いません。

検証は番号付きWAV、模擬コマンドによるUSB／WPRの開始・停止・失敗・状態通知、共通GUI操作、ファイルの関連・ZIP・再開を対象にしています。開発環境では実プロバイダーとキーワードの読み取り、Logmanのヘルプ確認を行いました。管理者での実USB ETL取得と対象機器でのイベント内容は未検証です。対象PCで取得して解析する必要があります。
